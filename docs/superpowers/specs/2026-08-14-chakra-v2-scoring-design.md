# 脉轮测试 V2 双入口与计分设计

- 日期：2026-08-14
- 状态：已确认
- 适用仓库：`chakras-yuanstudio`

## 1. 背景

当前脉轮测试以 Next.js 全局 `basePath: "/chakras"` 运行，欢迎页、答题页、结果页、静态资源和 API 都使用 `/chakras` 前缀。用户需要在不改变 V1 的前提下增加 V2：

- V1 继续使用 `/chakras`；
- V2 使用新地址 `/chakra`；
- 两个版本的前端界面完全一致；
- V2 只调整海底轮计分；
- 两个版本的浏览器答题进度和结果完全隔离；
- 后台记录继续写入同一张表，不区分版本。

## 2. 目标

1. 保持 V1 地址、计分、历史本地结果和现有部署路径不变。
2. 让 `/chakra` 显示与 V1 相同的前端，并启用 V2 计分。
3. V2 海底轮最终分数在 V1 分数基础上增加 20 分，最高不超过 100 分。
4. V1 和 V2 使用不同的浏览器存储键，互不恢复、覆盖或清理对方数据。
5. 结果页、人物原型、本地结果和 API 请求始终使用同一份版本化分数。

## 3. 非目标

- 不修改题目、选项或其原始分值。
- 不修改其余六个脉轮的计分。
- 不复制欢迎页、答题页、结果页或 CSS。
- 不新增数据库表、字段或迁移。
- 不回算或迁移历史测试记录。
- 不为用户增加版本切换按钮。
- 不改变主题存储；V1 和 V2 继续共用外观主题偏好。

## 4. 已确认决策

### 4.1 双入口方式

保留现有 Next.js `basePath: "/chakras"` 和单一构建。由 Nginx 将浏览器请求 `/chakra` 内部改写到现有应用的 `/chakras` 页面，浏览器地址栏保持 `/chakra`。

这样可以继续复用现有 `/chakras/_next/*`、字体、二维码、人物图片和 API，不需要重构 V1 的静态资源契约。

### 4.2 版本识别

服务端仍按 `/chakras` 渲染同一首屏。版本初始状态必须是“未解析”，现有“正在恢复测试”首屏在此期间不访问任何测试存储键。客户端挂载后先读取 `window.location.pathname`：

- `/chakra` 或 `/chakra/`：V2；
- 其他路径：V1。

路径解析完成后，未知路径得到 V1，避免 V1 因识别失败意外使用新规则。只有获得明确的 V1 或 V2 后才能恢复会话、注册进度保存逻辑或执行任何测试存储操作。当前应用没有 `next/link` 或客户端路由跳转；如果以后增加多页面导航，需要重新评估单一 `basePath` 下的别名行为。

### 4.3 V2 计分公式

先按现有逻辑计算、四舍五入并限制每个脉轮到 `-100..100`，然后只对 V2 海底轮应用：

```text
V2 海底轮分数 = min(V1 海底轮分数 + 20, 100)
```

示例：

| V1 海底轮 | V2 海底轮 |
|---:|---:|
| -100 | -80 |
| 0 | 20 |
| 25 | 45 |
| 80 | 100 |
| 100 | 100 |

计分函数接收可选版本参数，省略时默认 V1。未传版本的现有调用和测试必须保持原行为。

## 5. 架构设计

### 5.1 共享前端

两个入口继续渲染同一个 `Home`、同一个 `useTestSession` 和同一组页面组件。版本只作为业务配置进入会话与计分层，不在组件树中复制页面，也不增加 V2 专属样式。

新增 `src/lib/test-version.ts`，只负责 `TestVersion` 类型、浏览器路径到版本的解析，以及两个版本的公开分享地址。`useTestSession` 的初始版本为 `null`，在现有启动 effect 中先解析版本，再恢复对应会话；解析前保持 `booting`，不得读取、写入或清除任何测试存储键。解析完成后，会话层保存非空的 `TestVersion`，所有后续存储操作都显式使用该版本对应的键。

### 5.2 浏览器存储隔离

V1 保留现有键，保证历史数据可继续恢复：

```text
chakra-test-answers
chakra-test-current-question
chakra-test-result
```

V2 使用新键：

```text
chakra-test-v2-answers
chakra-test-v2-current-question
chakra-test-v2-result
```

恢复、暂存、提交、清除和重测都必须接收当前版本对应的同一组键。V2 不读取旧 V1 结果，也不在首次访问时迁移数据。

主题键 `chakra-test-theme-v1` 继续共用，因为主题不是测试进度或结果。

### 5.3 提交数据流

```text
浏览器地址
  -> 解析 V1/V2
  -> 读取该版本的本地答案
  -> 完成 56 题
  -> 按版本计算七轮分数
  -> 生成不可变提交快照
  -> 保存到该版本的本地结果键
  -> 使用同一快照渲染结果页
  -> POST 到现有 /chakras/api/test-results
```

V2 加分发生在创建提交快照之前。因此以下消费者天然一致：

- 主导、辅助和最低脉轮排序；
- 人物原型与分析文案；
- 七轮图和整体平均分；
- 本地结果恢复；
- API 请求和数据库中的 `rootScore`。

### 5.4 API 与数据库

V1 和 V2 继续调用 `/chakras/api/test-results`，请求体保持 `deviceId`、`scores`、`answers` 不变。API 不重新计算分数，继续保存客户端提交快照。

数据库继续使用现有 `TestResult` 表，不增加版本字段。V1 和 V2 记录在后台不可区分，这是本次明确接受的产品约束。

### 5.5 分享地址

结果页外观和操作不变，但复制出的分享文案按当前版本选择入口：

- V1：`https://yyry.studio/chakras`
- V2：`https://yyry.studio/chakra`

会话层将已解析的 `TestVersion` 返回给页面，页面再把它作为显式 prop 传给 `ResultPage`。结果页调用 `test-version.ts` 中的分享地址函数，不自行重复读取浏览器路径。

## 6. Nginx 契约

仓库中没有线上 Nginx 配置，因此代码实现不直接假设上游名称或端口。上线前必须先读取实际配置，并基于现有 `/chakras` location 生成可直接应用的配置片段。新增规则必须满足：

1. 使用精确匹配处理 `/chakra`，不得让 `/chakrafoo` 等路径命中；
2. 将 `/chakra` 连同原查询参数内部改写到同一上游的 `/chakras` 根页面；
3. 不对主入口发送 301/302/307/308 到 `/chakras`，浏览器地址和 `window.location.pathname` 保持 `/chakra`；
4. `/chakra/` 只允许精确匹配，可内部改写，或在保留查询参数的前提下统一重定向到 `/chakra`；
5. 不新增 `/chakra/*` 前缀代理，不影响现有 `/chakras/_next/*`、公共资源和 API；
6. 代理头、超时和上游与现有 `/chakras` 配置一致，现有 `/chakras` location 不改动。

部署交付物必须包含最终生效的 Nginx location 片段或等价配置记录，不能只以 `/chakra` 偶然返回 200 作为路由正确的证据。

V2 HTML 继续引用 `/chakras/_next/*` 和 `/chakras/*` 公共资源，这是方案的预期行为，不代表测试数据未隔离。

## 7. 错误处理与兼容性

- 版本识别失败时使用 V1。
- 本地存储不可用时沿用现有告警和内存回退，不访问另一版本的键。
- API 保存失败时沿用现有“本地结果已保存、在线备份失败”行为。
- V1 历史结果按原分数展示，不自动套用 V2 加分。
- V2 没有历史结果时从空状态开始。
- Nginx 未配置前，`/chakra` 返回 404；这属于部署未完成，而不是前端降级路径。

## 8. 测试设计

### 8.1 计分单元测试

先写失败测试，再实现最小逻辑：

- 56 题全选中间项：省略版本和显式传入 V1 都得到海底轮 `0`，V2 得到 `20`；
- 只让海底轮第 2、3 题选择下标 `0`：V1 为 `25`，V2 为 `45`；
- 海底轮第 1、4、5、7、8 题选择 `4`，第 2 题选择 `0`，第 3 题选择 `1`，第 6 题选择 `2`：原始和为 `81.25`，V1 先四舍五入为 `81`，V2 再加分并封顶为 `100`；
- 海底轮正向题选择 `4`、反向题选择 `0`：V1 和 V2 都封顶为 `100`；
- 海底轮正向题选择 `0`、反向题选择 `4`：V1 为 `-100`，V2 为 `-80`；
- 每个 V2 用例中其余六轮与 V1 相同。

### 8.2 存储单元测试

- V1 和 V2 键集合不同；
- V2 恢复不读取 V1 进度或结果；
- V2 保存不覆盖 V1；
- V2 重测只清除 V2；
- V1 原有恢复、保存和清理测试继续通过。

### 8.3 会话集成测试

- 在 `/chakra` 环境完成提交后，页面结果、本地 V2 结果和 API 请求体中的海底轮分数一致；
- 在 `/chakras` 环境完成相同答案后仍得到 V1 分数；
- 两个版本提交后，双方本地结果均保留；
- V2 分享文案包含 `/chakra`，V1 仍包含 `/chakras`。

### 8.4 仓库验证

```text
npm test
npm run lint
npx tsc --noEmit
npm run build
```

构建配置当前允许忽略 TypeScript 构建错误，因此必须单独运行 TypeScript 检查，不能只以构建成功作为正确性证据。

### 8.5 路由验收

在临时本地反向代理或线上 Nginx 生效后验证：

- `/chakra` 返回 200，刷新后仍为 200；
- `/chakra?source=v2` 返回 200且查询参数保留；
- `/chakrafoo` 不命中 V2 入口；
- 地址栏不跳转到 `/chakras`；
- 页面脚本、字体、二维码和人物图无 404；
- V2 完整答题、续存、结果、分享和重测可用；
- `/chakras` 的相同流程与原计分保持不变；
- 桌面端和移动端布局与 V1 一致。

本地或线上人工验收不得直接向真实的 `POST /chakras/api/test-results` 写入测试记录。默认使用临时代理或浏览器 mock 拦截该请求；只有获得单独、明确的数据库集成验收授权后，才允许创建可识别且可清理的测试记录。

## 9. 预计代码范围

只修改与版本识别、计分、存储和分享直接相关的文件：

- `src/lib/chakra-data.ts` 及其测试；
- `src/lib/test-session.ts` 及其测试；
- `src/hooks/use-test-session.ts` 及其测试；
- `src/app/page.tsx` 及其测试；
- `src/components/result-page.tsx` 及其测试；
- 新增 `src/lib/test-version.ts` 及其测试。

不修改 Prisma schema、题库、页面视觉结构与样式、全局样式或现有静态资源。

## 10. 成功标准

1. `/chakras` 使用 V1 计分并继续恢复既有本地数据。
2. `/chakra` 使用 V2 计分，海底轮加 20 且不超过 100。
3. V1/V2 的答题进度、结果与重测清理完全隔离。
4. 两个版本共用现有 API 和数据库表。
5. 前端结构与视觉相同，没有复制页面代码。
6. 自动化测试、ESLint、TypeScript 检查和生产构建通过。
7. Nginx 生效后，两条线上地址均可刷新访问且资源请求正常。

## 11. 回滚

如果 V2 出现问题，先删除或停用 Nginx 的 `/chakra` 映射，即可立即关闭新入口；`/chakras` 不依赖该映射。代码层默认仍为 V1，因此 V2 入口关闭后不会改变现有用户行为。V2 本地存储使用独立键，回滚不会污染 V1 历史数据。
